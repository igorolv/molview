# Задание: «Строение молекул», версия третья — сцена на VTK

Третья версия программы. Первая была на TypeScript (`molview/`), вторая — на C++
с собственным рендером на GDI+ (`molviewcpp/`). Здесь меняется ровно одно:
**сцену рисует VTK**, промышленная библиотека научной визуализации, на которой
построены ParaView и 3D Slicer.

Всё остальное — расчёт, интерфейс, каталог, панель разбора — остаётся своим и
переезжает без изменений.

## 2. Цель и ограничения

Получить ту же программу, но с картинкой уровня научной публикации: объёмное
затенение, студийный свет, тени, настоящие изоповерхности орбиталей, экспорт
кадра в 4K.

Ограничения:

1. **Внешние библиотеки теперь разрешены** — это главное отличие от второй
   версии. Разрешены VTK и то, что она тянет за собой. Ничего сверх этого
   добавлять не нужно: ни Qt, ни boost, ни json-библиотек. Свой разбор JSON
   уже написан и работает.
2. **Ядро `src/chem/` по-прежнему не знает про Windows и не знает про VTK.**
   Проверяемое требование: `grep -rE "windows.h|vtk" src/chem/` обязан быть
   пустым. Ядро считает — VTK показывает. Эта граница и есть ответ на вопрос
   «что здесь твоё».
3. **Сверка с эталоном обязана продолжать проходить.** `data/reference.json`
   не трогается, средняя ошибка предсказания валентного угла остаётся 1,68°.
   Любое расхождение означает, что при переносе что-то сломано.
4. **Тулчейн — MSYS2/MINGW64.** w64devkit здесь не годится: VTK из пакета
   собрана другим g++, и сборки libstdc++ не совместимы по ABI.
5. Единого статического `.exe` больше не будет — VTK динамическая. Рядом с
   программой ляжет набор DLL. Это осознанная плата за библиотеку.

## 3. Настройка среды (первый шаг)

Весь раздел проверен на практике 10 сентября 2026 года: описанное ниже
проделано целиком и закончилось работающей пробой.

1. Поставить MSYS2 — из обычного терминала Windows одной командой:

```
winget install --id MSYS2.MSYS2 -e --accept-package-agreements --accept-source-agreements
```

Встаёт в `C:\msys64`, прав администратора не требует. Кто предпочитает
установщик руками — https://www.msys2.org/, там тот же файл.

2. **Сразу поправить список зеркал, иначе ничего не скачается.** Первым в
   списке стоит `mirror.msys2.org`, который отвечает редиректом 302 в никуда;
   pacman вываливается с `Operation too slow. Less than 1 bytes/sec transferred`
   и выглядит это как проблема с интернетом, хотя интернет ни при чём. Следующий
   в списке `repo.msys2.org` работает нормально. Лечение — закомментировать
   первую строку в обоих списках:

```bash
sed -i 's|^Server = https://mirror.msys2.org|#&|' \
    /etc/pacman.d/mirrorlist.msys /etc/pacman.d/mirrorlist.mingw
```

Не помешает и `ParallelDownloads = 1` в `/etc/pacman.conf`: при пяти
параллельных загрузках сервер чаще рвёт соединение.

3. Запустить **`mingw64.exe`** — именно его, а не `msys2.exe` и не `ucrt64.exe`.
   Это разные оболочки с разными компиляторами в `PATH`, и половина чужих бед
   в интернете начинается с того, что человек собирает не в той.

4. Обновить систему пакетов:

```bash
pacman -Syu
```

Первый проход обновит сам pacman и **закроет окно** — это нормально. Открыть
`mingw64.exe` заново и повторить ту же команду.

5. Поставить всё нужное:

```bash
pacman -S mingw-w64-x86_64-toolchain \
          mingw-w64-x86_64-cmake \
          mingw-w64-x86_64-ninja \
          mingw-w64-x86_64-vtk \
          mingw-w64-x86_64-nlohmann-json \
          mingw-w64-x86_64-fast_float \
          mingw-w64-x86_64-libpng
```

Около 1,8 ГБ. На вопрос про состав группы `toolchain` — просто Enter.

Последние три пакета — **не прихоть**. Пакет VTK не объявляет их своими
зависимостями, но её файлы настройки CMake на них ссылаются, и без них
`find_package(VTK)` падает с `The link interface of target "VTK::nlohmannjson"
contains: nlohmann_json::nlohmann_json but the target was not found`. Ошибка
выглядит как поломка внутри VTK, хотя это просто недостающий пакет. `libpng`
понадобится позже, для экспорта кадра.

Что получилось при проверке: g++ 16.2.0, CMake 4.4.3, Ninja 1.13.2, VTK 9.6.2
со всеми модулями — `DomainsChemistry` внутри.

6. **Собрать пробу.** Она лежит в `probe/` и проверяет разом весь технический
   риск проекта: линкуется ли VTK, на месте ли модуль химии, отработал ли
   `vtk_module_autoinit`, работает ли закадровый рендер на этой видеокарте,
   и укладывается ли перенос кадра в бюджет времени.

```bash
cd /c/git/fun/molviewvtk/probe
cmake -B build -G Ninja
cmake --build build
./build/probe.exe
```

Диск `C:` в MSYS2 виден как `/c`; обратные слэши не работают.

**Что получилось при проверке** (GeForce GT 1030, окно 884×661):

```
Проба VTK — рендер 2.2 мс · чтение 2.5 мс · вывод 2.0 мс · всего 6.6 мс
```

Окно с вращающимся метаном, силуэты гладкие, в углублениях между атомами
видно затенение. Запас по времени двукратный: 6,6 мс при бюджете кадра 16,7.
Стоит заметить, что сам рендер занимает лишь треть — 4,5 мс уходит на чтение
кадра и вывод, и это постоянная плата за закадровую схему из раздела 5.

**Не начинать работу над сценой, пока проба не прошла.** Что делать, если
не прошла — раздел 10.

7. Собрать сам проект — он пока без VTK и должен работать как вторая версия:

```bash
cmake -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
./build/molview.exe
```

## 5. Схема встраивания: почему закадровый рендер

Решение принято сознательно, и его стоит понимать, потому что очевидный путь
здесь — неправильный.

**Очевидный путь.** У VTK есть штатный способ жить внутри чужого окна:
`vtkWin32OpenGLRenderWindow::SetParentId(hwnd)`. VTK заводит дочернее окно и
рисует в него. Работает, документировано, пять строк.

**Почему он не годится.** Дочернее окно владеет своим прямоугольником целиком,
и Windows отсекает всё, что чужой код пытается нарисовать поверх. А на нынешней
раскладке поверх сцены лежат четыре вещи: заголовок молекулы, строка подсказки,
легенда справа вверху и плавающая панель инструментов внизу. Все они рисуются
в `panel.cpp`, все выглядят хорошо, и все пришлось бы либо выносить из области
сцены, либо переписывать средствами VTK. То есть «сохраним интерфейс» на деле
означало бы «переделаем раскладку».

**Что делается вместо этого.** VTK рисует не в окно, а в кадровый буфер, кадр
забирается в память и выводится в тот же самый растр, в который рисует GDI+ —
под интерфейсом. Порядок кадра:

```
WM_PAINT
  ├─ 1. VTK: Render() в закадровый буфер
  ├─ 2. GetRGBACharPixelData() — кадр в память
  ├─ 3. StretchDIBits() кадра в область сцены памятного растра
  ├─ 4. GDI+ поверх: каталог, панель разбора, панель инструментов, заголовок
  └─ 5. BitBlt памятного растра на экран
```

Пункты 4 и 5 уже написаны и работают. Добавляются 1–3, это и есть `scene/frame.cpp`.

Две мелочи, на которых легко споткнуться:

* OpenGL отдаёт строки снизу вверх. DIB с **положительной** высотой в
  `BITMAPINFOHEADER` тоже идёт снизу вверх — значит переворачивать кадр не надо.
  Это приятная случайность, и её стоит записать комментарием, иначе кто-нибудь
  «исправит».
* OpenGL отдаёт RGBA, DIB ждёт BGRA. Нужен обмен красного и синего — простой
  цикл, около миллисекунды на кадр 1000×700.

**Зеркальность — то, о чём легко не догадаться.** Собственная проекция кладёт
мировой +x ВПРАВО, а правосторонняя камера при взгляде с −z кладёт его влево:
направление «вправо» у неё равно forward × up = z × y = −x. Расхождение ровно
в одну ось, то есть картинка VTK получается зеркальной по горизонтали. Если
этого не заметить, всё будет выглядеть правдоподобно — на симметричных
молекулах вроде воды и углекислого газа разницы не видно вообще, — но
хиральные молекулы поедут в свой антипод.

Разворот делается в `frame.cpp` при переносе кадра, в том же цикле, который
и так меняет местами красный с синим. В матрицу отражение вносить нельзя:
у неё станет отрицательный определитель, вывернет нормали и испортит
освещение.

Проверяется это на **несимметричной** молекуле — годится пероксид водорода:
выключить вращение, сбросить вид и сравнить снимок со второй версией. Обе
должны показать один и тот же разворот.

**Мышь и камера.** Интерактор VTK не используется вовсе: `interactor->Start()`
забрал бы себе цикл сообщений. Существующий код в `window.cpp` уже ловит
перетаскивание и колесо — он просто начинает звать `vtkCamera`:

| Действие | Было | Стало |
|---|---|---|
| перетаскивание | своя матрица поворота | `camera->Azimuth(-dx*0.3)`, `camera->Elevation(dy*0.3)`, затем `OrthogonalizeViewUp()` |
| колесо | `zoom *= k` | `camera->Dolly(k)`, затем `renderer->ResetCameraClippingRange()` |
| двойной щелчок | сброс вида | `renderer->ResetCamera()` |
| щелчок по атому | свой `hitTest` | `vtkHardwareSelector` — `vtkMoleculeMapper` умеет отдавать по нему номера выбранных атомов и связей |

Свой `hitTest` из `renderer.cpp` после этого не нужен.

## 6. Что берёт на себя VTK и что остаётся своим

| Задача | Кто делает |
|---|---|
| Разбор формулы, названия, SMILES | своё, `chem/` |
| Неявные водороды, делокализация, циклы | своё, `chem/` |
| Теория Гиллеспи, стерическое число, тип AXE | своё, `chem/` |
| Трёхмерные координаты, релаксация | своё, `chem/` |
| Валентные углы, диполь, полярность | своё, `chem/` |
| Волновые функции орбиталей на сетке | своё, `chem/orbital.cpp` — **новое** |
| Шары и связи, три стиля модели | VTK, `vtkMoleculeMapper` |
| Затенение, свет, тени, сглаживание | VTK, настройки `vtkRenderer` |
| Изоповерхность по сетке орбитали | VTK, `vtkFlyingEdges3D` |
| Выбор атома мышью | VTK, `vtkHardwareSelector` |
| Дуги углов, облака НЭП, стрелка диполя | своё, из примитивов VTK |
| Каталог, поиск, панель разбора, кнопки | своё, `ui/` на GDI+ |

Соотношение получается такое: VTK отвечает за то, как молекула выглядит,
`chem/` — за то, какая она. Второе и есть содержание проекта.

**Данные передаются так:**

```cpp
vtkNew<vtkMolecule> molecule;
std::vector<vtkIdType> ids;
for (const chem::Atom& atom : analysis.molecule.atoms) {
    // в ядре элемент хранится символом; номер берётся из справочника
    const int z = chem::element(atom.el).z;
    ids.push_back(molecule->AppendAtom(static_cast<unsigned short>(z),
                                       atom.pos.x, atom.pos.y, atom.pos.z).GetId());
}
for (const chem::Bond& bond : analysis.molecule.bonds) {
    molecule->AppendBond(ids[bond.a], ids[bond.b], vtkOrder(bond.order));
}
```

**Дробные кратности — отдельный случай, и его надо решить сразу.** В ядре
`Bond::order` вещественный: у ароматической связи он 1,5, у делокализованной
в нитрат-ионе — 1⅓. `vtkMolecule::AppendBond` принимает целое, и
`vtkMoleculeMapper` умеет рисовать только одинарную, двойную и тройную.

Как поступать: `vtkOrder()` округляет вниз до целого — то есть делокализованная
связь уезжает в VTK как одинарная, — а признак `bond.delocalized` при этом не
теряется, и такие связи дорисовываются своими средствами: тонкий пунктирный
цилиндр или кольцо внутри ароматического цикла. Это часть работы этапа 4,
и во второй версии соответствующий код уже есть — его логику можно взять
оттуда.

Три стиля модели с панели инструментов ложатся на готовые режимы:

| Кнопка | Вызов |
|---|---|
| Шары | `mapper->UseBallAndStickSettings()` |
| Объём | `mapper->UseVDWSpheresSettings()` |
| Каркас | `mapper->UseLiquoriceStickSettings()` |

Есть смысл сверить свой `data/elements.json` с `vtkPeriodicTable`: цвета CPK,
ковалентные и ван-дер-ваальсовы радиусы. Совпадение — хороший абзац в записку,
расхождение — повод разобраться, чьи данные свежее.

## 7. Качество картинки

По умолчанию VTK выглядит как программа 2005 года: одна лампа, плоский свет,
лесенки на краях. Всё, ради чего затевалась третья версия, включается руками:

```cpp
renderer->SetUseSSAO(true);        // затенение в щелях между атомами —
renderer->SetSSAORadius(0.5);      // главный источник ощущения объёма
renderer->SetSSAOBias(0.01);
renderer->SetSSAOKernelSize(32);
renderer->SetSSAOBlur(true);

renderer->SetUseFXAA(true);        // сглаживание краёв
renderer->SetUseDepthPeeling(true);// честная прозрачность для орбиталей и НЭП
renderer->SetMaximumNumberOfPeels(8);

vtkNew<vtkLightKit> lights;        // трёхточечная студийная схема:
lights->AddLightsToRenderer(renderer);  // ключевой, заполняющий, контровой
```

Дальше по вкусу: `vtkShadowMapPass` в цепочке проходов рендера даёт тени;
`actor->GetProperty()->SetInterpolationToPBR()` вместе с металличностью и
шероховатостью — физически достоверные материалы.

Порядок работы над картинкой: сначала включить SSAO и свет и посмотреть, что
получилось. Скорее всего этого уже хватит, а тени и PBR окажутся украшением,
которое стоит своих хлопот только если останется время.

**Экспорт кадра.** `vtkWindowToImageFilter` с `SetScale(3)` и `vtkPNGWriter`
дают кадр 3000×2100 для пояснительной записки и презентации. Это то, чего во
второй версии нет вообще, и то, что сразу видно на защите.

## 8. Орбитали как изоповерхности — новая работа в ядре

Во второй версии лепестки гибридных орбиталей нарисованы кривыми Безье «на
глаз». Здесь они считаются.

В `chem/orbital.cpp` (Windows и VTK не знает, значит **проверяется тестами**):

Водородоподобные функции в атомных единицах, с точностью до нормировки:

* `2s`: ψ ∝ (2 − r) · e^(−r/2)
* `2p_z`: ψ ∝ z · e^(−r/2), и так же для `p_x`, `p_y`

Гибриды как их линейные комбинации:

* `sp³` вдоль направления **d**: ψ = ½·s + (√3/2)·p_**d**
* `sp²`: ψ = (1/√3)·s + (√2/√3)·p_**d**
* `sp`: ψ = (1/√2)·(s ± p_z)

где p_**d** = d_x·p_x + d_y·p_y + d_z·p_z — проекция набора p-орбиталей на
направление гибрида, а сами направления **уже посчитаны**: они лежат в
`AtomAnalysis::orbitalDirs` — единичные векторы всех гибридных орбиталей,
включая связывающие, которые ставит теория Гиллеспи. Придумывать их не надо,
надо только подставить.

Функция отдаёт значения на равномерной сетке в кубе вокруг центрального атома
(разумно 64³ точек на ±4 Å), а `scene/` кладёт их в `vtkImageData` и проводит
`vtkFlyingEdges3D` по двум уровням — `+iso` и `−iso`. Получаются две
поверхности, разного знака и разного цвета: ровно то, как орбитали рисуют
в учебниках, только посчитанное.

Что проверять в `tests/orbitaltest.cpp`:

1. нормировка: сумма ψ² по сетке, умноженная на объём ячейки, близка к единице;
2. узловая плоскость: у `p_z` значения при z = 0 равны нулю;
3. углы между гибридами: между четырьмя sp³ — 109,47°, между тремя sp² —
   120°, между двумя sp — 180°. Считается по положению максимума каждого
   гибрида;
4. ортонормированность: скалярное произведение разных гибридов по сетке — ноль,
   одинаковых — единица.

Пункт 3 стоит отдельного упоминания в записке: он показывает, что тетраэдрический
угол не постулируется, а получается из математики.

## 9. Порядок работы

**Этап 1. Проба и переезд. СДЕЛАНО.** Раздел 3. Программа собирается через
CMake в MINGW64, работает как вторая версия, `ctest` проходит.

**Этап 2. Сцена вместо старого рендера. СДЕЛАНО.** `scene/frame.cpp` —
закадровый рендер и перенос кадра; `scene/scene.cpp` — `vtkMolecule` из
разбора, `vtkMoleculeMapper`, камера от собственного рендера. Шары и связи
рисует VTK, три стиля модели переключаются, дуги углов, НЭП, орбитали, диполь
и подписи пока рисуются по-старому поверх кадра.

Замеры на GT 1030, область сцены 662×721: **сцена 3,2 мс, перенос 0,5 мс**.
Перенос дешевле, чем в пробе, потому что `AlphaBlend` в память быстрее, чем
`StretchDIBits` в окно.

Что осталось за пределами этапа и ждёт следующих:

* НЭП и орбитали ложатся ПОВЕРХ шаров даже когда должны быть за ними —
  сортировки по глубине между GDI+ и VTK нет и быть не может (этап 4);
* подписи элементов и дуги углов тоже без проверки глубины (этап 4);
* анимации появления атомов больше нет — она жила в старом сборщике примитивов;
* затуманивание дальних атомов потеряно, вместо него на этапе 3 придут
  затенение и тени;
* цвета атомов — стандартная палитра CPK из VTK, а не своя, подогнанная под
  тёмный фон. Внутренняя таблица цветов `vtkMoleculeMapper` не подменяется,
  так что своя палитра потребует отказа от `DiscreteByAtom` (этап 3).

**Этап 3. Качество.** Раздел 7: SSAO, свет, сглаживание, прозрачность.
Здесь же — экспорт в PNG.

**Этап 4. Наложения средствами VTK.** Дуги углов (`vtkArcSource`), подписи
(`vtkBillboardTextActor3D`), стрелка диполя (`vtkArrowSource` с поворотом),
облака НЭП. Смысл переноса в том, что они начинают правильно перекрываться
с атомами по глубине, чего при рисовании поверх кадра быть не может.

**Этап 5. Орбитали.** Раздел 8. Самая интересная часть, и делать её надо
последней: до неё всё остальное должно уже работать.

`renderer.cpp` и `renderer.h` удаляются после этапа 4.

## 10. Грабли

Список составлен заранее, чтобы не терять на каждой по полдня.

* **Чёрный экран без единой ошибки** — забыт `vtk_module_autoinit` в
  `CMakeLists.txt`. Собирается, запускается, ничего не рисует. Это первое, что
  надо проверять при любой непонятной пустоте.
* **Не та оболочка.** Собирать только в `mingw64.exe`. В MSYS-оболочке другой
  компилятор, и VTK для него не собрана.
* **`find_package(VTK)` падает на «target not found».** Не хватает пакетов
  `nlohmann-json` и `fast_float`, которые VTK не объявляет зависимостями,
  см. раздел 3, шаг 5.
* **`CustomArrayRadius` молча не работает.** Массив `radii` добавлен в
  `molecule->GetAtomData()`, имя правильное, тип `float` — а маппер рисует
  ПУСТОТУ. Причина: конвейер VTK смотрит на время изменения ВХОДА, и
  `AddArray` его не поднимает. Лечится `molecule->Modified()` сразу после
  `AddArray`. Ошибки нет ни при сборке, ни при запуске.
* **Кадр переносится, а на экране ничего.** Прежде чем искать причину в VTK,
  стоит проверить сам цикл переноса: на этапе 2 указатель приёмника не
  двигался по строке, писался только первый пиксель каждой строки. Со стороны
  выглядело в точности как неработающая прозрачность. Полезный приём для
  разбора: выгрузить кадр в `.bmp` прямо из программы и посмотреть на него —
  это сразу отделяет «VTK не нарисовала» от «перенос сломан».
* **Молекула вышла крошечной посреди пустого кадра.** `ResetCamera()` позвана
  до первого `Render()`: маппер геометрию ещё не построил, границы сцены пусты,
  и камера наводится в никуда. Наводить камеру надо после первого кадра.
  На этом споткнулась проба при первом запуске.
* **Смешивание с w64devkit.** Если в `PATH` окажется его g++, сборка пройдёт,
  а программа упадёт при запуске: у сборок libstdc++ разный ABI.
* **Кириллица в подписях VTK.** Встроенный шрифт её не знает, вместо букв будут
  прямоугольники. Лечение:
  `property->SetFontFamily(VTK_FONT_FILE)` и
  `property->SetFontFile("C:/Windows/Fonts/segoeui.ttf")`.
* **DLL рядом с программой.** Список зависимостей снимается через
  `ldd build/molview.exe`, всё из `mingw64/bin` копируется рядом с `.exe`.
  Готового инструмента для этого у VTK нет, придётся написать скрипт.
* **Статическая компоновка.** Флаги `-static-libstdc++` и прочие надо убрать
  из `CMakeLists.txt`, когда появится VTK, иначе компоновка не сойдётся.
* **`CMAKE_BUILD_TYPE`.** Если не задать, CMake собирает без оптимизации.
  В `CMakeLists.txt` это уже предусмотрено, но при ручной настройке легко
  потерять и потом удивляться, почему всё медленно.
* **Если закадровый рендер не заработает** (проба показывает чёрный кадр,
  хотя `autoinit` на месте) — отступаем к дочернему окну: убрать
  `SetShowWindow(false)` и `SetUseOffScreenBuffers(true)`, позвать
  `SetParentId(hwnd)`. Тогда раздел 5 отменяется, панель инструментов и
  заголовок выносятся полосами над и под областью сцены, а `panel.cpp`
  правится в части раскладки.

## 11. Соглашения

Те же, что во второй версии:

* C++17, `-Wall -Wextra`, без предупреждений;
* исходники в UTF-8, сборка с `-finput-charset=UTF-8 -fexec-charset=UTF-8`,
  Windows API — широкими строками;
* комментарии и строки интерфейса по-русски, комментарии объясняют **почему**;
* именование: типы `PascalCase`, функции и переменные `camelCase`;
* заголовки самодостаточны, `#pragma once`;
* **никаких «улучшений» алгоритмов ядра по ходу дела.** Калибровочные
  константы, веса групп, коэффициенты релаксации, масштаб диполя — не трогать:
  эталон снят именно с ними.

## 13. Чего делать не надо

* **Не переходить на Qt.** Интерфейс уже написан и работает; переписывать его
  на виджеты — потерянная неделя без единого нового результата на экране.
* **Не звать `interactor->Start()`.** Цикл сообщений свой.
* **Не подключать OSPRay и трассировку лучей.** Это отдельная зависимость,
  и SSAO с тенями даёт девять десятых эффекта за одну сотую хлопот.
* **Не добавлять молекул в базу** — она общая с первой версией, любое
  расхождение ломает сверку с эталоном.
* **Не переносить `chem/` на структуры данных VTK.** Соблазн есть:
  у `vtkMolecule` тоже есть атомы и связи. Но тогда ядро перестанет быть
  проверяемым отдельно, а вместе с ним исчезнет и ответ на вопрос, что в
  проекте сделано своими руками.
