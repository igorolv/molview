# Задание: «Строение молекул», версия третья — сцена на VTK

Третья версия программы. Первая была на TypeScript (`molview/`), вторая — на C++
с собственным рендером на GDI+ (`molviewcpp/`). Здесь меняется ровно одно:
**сцену рисует VTK**, промышленная библиотека научной визуализации, на которой
построены ParaView и 3D Slicer.

Всё остальное — расчёт, интерфейс, каталог, панель разбора — остаётся своим и
переезжает без изменений.

## 2. Цель и ограничения

Получить ту же программу, но с картинкой уровня научной публикации: объёмное
затенение, студийный свет, тени, настоящие изоповерхности орбиталей, экспорт
кадра в 4K.

Ограничения:

1. **Внешние библиотеки теперь разрешены** — это главное отличие от второй
   версии. Разрешены VTK и то, что она тянет за собой. Ничего сверх этого
   добавлять не нужно: ни Qt, ни boost, ни json-библиотек. Свой разбор JSON
   уже написан и работает.
2. **Ядро `src/chem/` по-прежнему не знает про Windows и не знает про VTK.**
   Проверяемое требование: `grep -rE "windows.h|vtk" src/chem/` обязан быть
   пустым. Ядро считает — VTK показывает. Эта граница и есть ответ на вопрос
   «что здесь твоё».
3. **Сверка с эталоном обязана продолжать проходить.** `data/reference.json`
   не трогается, средняя ошибка предсказания валентного угла остаётся 1,68°.
   Любое расхождение означает, что при переносе что-то сломано.
4. **Тулчейн — MSYS2/MINGW64.** w64devkit здесь не годится: VTK из пакета
   собрана другим g++, и сборки libstdc++ не совместимы по ABI.
5. Единого статического `.exe` больше не будет — VTK динамическая. Рядом с
   программой ляжет набор DLL. Это осознанная плата за библиотеку.

## 3. Настройка среды (первый шаг)

Весь раздел проверен на практике 10 сентября 2026 года: описанное ниже
проделано целиком и закончилось работающей пробой.

1. Поставить MSYS2 — из обычного терминала Windows одной командой:

```
winget install --id MSYS2.MSYS2 -e --accept-package-agreements --accept-source-agreements
```

Встаёт в `C:\msys64`, прав администратора не требует. Кто предпочитает
установщик руками — https://www.msys2.org/, там тот же файл.

2. **Сразу поправить список зеркал, иначе ничего не скачается.** Первым в
   списке стоит `mirror.msys2.org`, который отвечает редиректом 302 в никуда;
   pacman вываливается с `Operation too slow. Less than 1 bytes/sec transferred`
   и выглядит это как проблема с интернетом, хотя интернет ни при чём. Следующий
   в списке `repo.msys2.org` работает нормально. Лечение — закомментировать
   первую строку в обоих списках:

```bash
sed -i 's|^Server = https://mirror.msys2.org|#&|' \
    /etc/pacman.d/mirrorlist.msys /etc/pacman.d/mirrorlist.mingw
```

Не помешает и `ParallelDownloads = 1` в `/etc/pacman.conf`: при пяти
параллельных загрузках сервер чаще рвёт соединение.

3. Запустить **`mingw64.exe`** — именно его, а не `msys2.exe` и не `ucrt64.exe`.
   Это разные оболочки с разными компиляторами в `PATH`, и половина чужих бед
   в интернете начинается с того, что человек собирает не в той.

4. Обновить систему пакетов:

```bash
pacman -Syu
```

Первый проход обновит сам pacman и **закроет окно** — это нормально. Открыть
`mingw64.exe` заново и повторить ту же команду.

5. Поставить всё нужное:

```bash
pacman -S mingw-w64-x86_64-toolchain \
          mingw-w64-x86_64-cmake \
          mingw-w64-x86_64-ninja \
          mingw-w64-x86_64-vtk \
          mingw-w64-x86_64-nlohmann-json \
          mingw-w64-x86_64-fast_float \
          mingw-w64-x86_64-libpng
```

Около 1,8 ГБ. На вопрос про состав группы `toolchain` — просто Enter.

Последние три пакета — **не прихоть**. Пакет VTK не объявляет их своими
зависимостями, но её файлы настройки CMake на них ссылаются, и без них
`find_package(VTK)` падает с `The link interface of target "VTK::nlohmannjson"
contains: nlohmann_json::nlohmann_json but the target was not found`. Ошибка
выглядит как поломка внутри VTK, хотя это просто недостающий пакет. `libpng`
понадобится позже, для экспорта кадра.

Что получилось при проверке: g++ 16.2.0, CMake 4.4.3, Ninja 1.13.2, VTK 9.6.2
со всеми модулями — `DomainsChemistry` внутри.

6. **Собрать пробу.** Она лежит в `probe/` и проверяет разом весь технический
   риск проекта: линкуется ли VTK, на месте ли модуль химии, отработал ли
   `vtk_module_autoinit`, работает ли закадровый рендер на этой видеокарте,
   и укладывается ли перенос кадра в бюджет времени.

```bash
cd /c/git/fun/molviewvtk/probe
cmake -B build -G Ninja
cmake --build build
./build/probe.exe
```

Диск `C:` в MSYS2 виден как `/c`; обратные слэши не работают.

**Что получилось при проверке** (GeForce GT 1030, окно 884×661):

```
Проба VTK — рендер 2.2 мс · чтение 2.5 мс · вывод 2.0 мс · всего 6.6 мс
```

Окно с вращающимся метаном, силуэты гладкие, в углублениях между атомами
видно затенение. Запас по времени двукратный: 6,6 мс при бюджете кадра 16,7.
Стоит заметить, что сам рендер занимает лишь треть — 4,5 мс уходит на чтение
кадра и вывод, и это постоянная плата за закадровую схему из раздела 5.

**Не начинать работу над сценой, пока проба не прошла.** Что делать, если
не прошла — раздел 11.

7. Собрать сам проект — он пока без VTK и должен работать как вторая версия:

```bash
cmake -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
./build/molview.exe
```

## 5. Схема встраивания: почему закадровый рендер

Решение принято сознательно, и его стоит понимать, потому что очевидный путь
здесь — неправильный.

**Очевидный путь.** У VTK есть штатный способ жить внутри чужого окна:
`vtkWin32OpenGLRenderWindow::SetParentId(hwnd)`. VTK заводит дочернее окно и
рисует в него. Работает, документировано, пять строк.

**Почему он не годится.** Дочернее окно владеет своим прямоугольником целиком,
и Windows отсекает всё, что чужой код пытается нарисовать поверх. А на нынешней
раскладке поверх сцены лежат четыре вещи: заголовок молекулы, строка подсказки,
легенда справа вверху и плавающая панель инструментов внизу. Все они рисуются
в `panel.cpp`, все выглядят хорошо, и все пришлось бы либо выносить из области
сцены, либо переписывать средствами VTK. То есть «сохраним интерфейс» на деле
означало бы «переделаем раскладку».

**Что делается вместо этого.** VTK рисует не в окно, а в кадровый буфер, кадр
забирается в память и выводится в тот же самый растр, в который рисует GDI+ —
под интерфейсом. Порядок кадра:

```
WM_PAINT
  ├─ 1. VTK: Render() в закадровый буфер
  ├─ 2. GetRGBACharPixelData() — кадр в память
  ├─ 3. StretchDIBits() кадра в область сцены памятного растра
  ├─ 4. GDI+ поверх: каталог, панель разбора, панель инструментов, заголовок
  └─ 5. BitBlt памятного растра на экран
```

Пункты 4 и 5 уже написаны и работают. Добавляются 1–3, это и есть `scene/frame.cpp`.

Две мелочи, на которых легко споткнуться:

* OpenGL отдаёт строки снизу вверх. DIB с **положительной** высотой в
  `BITMAPINFOHEADER` тоже идёт снизу вверх — значит переворачивать кадр не надо.
  Это приятная случайность, и её стоит записать комментарием, иначе кто-нибудь
  «исправит».
* OpenGL отдаёт RGBA, DIB ждёт BGRA. Нужен обмен красного и синего — простой
  цикл, около миллисекунды на кадр 1000×700.

**Зеркальность — то, о чём легко не догадаться.** Собственная проекция кладёт
мировой +x ВПРАВО, а правосторонняя камера при взгляде с −z кладёт его влево:
направление «вправо» у неё равно forward × up = z × y = −x. Расхождение ровно
в одну ось, то есть картинка VTK получается зеркальной по горизонтали. Если
этого не заметить, всё будет выглядеть правдоподобно — на симметричных
молекулах вроде воды и углекислого газа разницы не видно вообще, — но
хиральные молекулы поедут в свой антипод.

Разворот делается в `frame.cpp` при переносе кадра, в том же цикле, который
и так меняет местами красный с синим. В матрицу отражение вносить нельзя:
у неё станет отрицательный определитель, вывернет нормали и испортит
освещение.

Проверяется это на **несимметричной** молекуле — годится пероксид водорода:
выключить вращение, сбросить вид и сравнить снимок со второй версией. Обе
должны показать один и тот же разворот.

**Мышь и камера.** Интерактор VTK не используется вовсе: `interactor->Start()`
забрал бы себе цикл сообщений. Существующий код в `window.cpp` уже ловит
перетаскивание и колесо — он просто начинает звать `vtkCamera`:

| Действие | Было | Стало |
|---|---|---|
| перетаскивание | своя матрица поворота | `camera->Azimuth(-dx*0.3)`, `camera->Elevation(dy*0.3)`, затем `OrthogonalizeViewUp()` |
| колесо | `zoom *= k` | `camera->Dolly(k)`, затем `renderer->ResetCameraClippingRange()` |
| двойной щелчок | сброс вида | `renderer->ResetCamera()` |
| щелчок по атому | свой `hitTest` | `vtkHardwareSelector` — `vtkMoleculeMapper` умеет отдавать по нему номера выбранных атомов и связей |

Свой `hitTest` из `renderer.cpp` после этого не нужен.

## 6. Что берёт на себя VTK и что остаётся своим

| Задача | Кто делает |
|---|---|
| Разбор формулы, названия, SMILES | своё, `chem/` |
| Неявные водороды, делокализация, циклы | своё, `chem/` |
| Теория Гиллеспи, стерическое число, тип AXE | своё, `chem/` |
| Трёхмерные координаты, релаксация | своё, `chem/` |
| Валентные углы, диполь, полярность | своё, `chem/` |
| Волновые функции орбиталей на сетке | своё, `chem/orbital.cpp` — **новое** |
| Шары и связи, три стиля модели | VTK, `vtkMoleculeMapper` |
| Затенение, свет, тени, сглаживание | VTK, настройки `vtkRenderer` |
| Изоповерхность по сетке орбитали | VTK, `vtkFlyingEdges3D` |
| Выбор атома мышью | VTK, `vtkHardwareSelector` |
| Дуги углов, облака НЭП, стрелка диполя | своё, из примитивов VTK |
| Каталог, поиск, панель разбора, кнопки | своё, `ui/` на GDI+ |

Соотношение получается такое: VTK отвечает за то, как молекула выглядит,
`chem/` — за то, какая она. Второе и есть содержание проекта.

**Данные передаются так:**

```cpp
vtkNew<vtkMolecule> molecule;
std::vector<vtkIdType> ids;
for (const chem::Atom& atom : analysis.molecule.atoms) {
    // в ядре элемент хранится символом; номер берётся из справочника
    const int z = chem::element(atom.el).z;
    ids.push_back(molecule->AppendAtom(static_cast<unsigned short>(z),
                                       atom.pos.x, atom.pos.y, atom.pos.z).GetId());
}
for (const chem::Bond& bond : analysis.molecule.bonds) {
    molecule->AppendBond(ids[bond.a], ids[bond.b], vtkOrder(bond.order));
}
```

**Дробные кратности — отдельный случай, и его надо решить сразу.** В ядре
`Bond::order` вещественный: у ароматической связи он 1,5, у делокализованной
в нитрат-ионе — 1⅓. `vtkMolecule::AppendBond` принимает целое, и
`vtkMoleculeMapper` умеет рисовать только одинарную, двойную и тройную.

Как поступать: `vtkOrder()` округляет вниз до целого — то есть делокализованная
связь уезжает в VTK как одинарная, — а признак `bond.delocalized` при этом не
теряется, и такие связи дорисовываются своими средствами: тонкий пунктирный
цилиндр или кольцо внутри ароматического цикла. Это часть работы этапа 4,
и во второй версии соответствующий код уже есть — его логику можно взять
оттуда.

Три стиля модели с панели инструментов ложатся на готовые режимы:

| Кнопка | Вызов |
|---|---|
| Шары | `mapper->UseBallAndStickSettings()` |
| Объём | `mapper->UseVDWSpheresSettings()` |
| Каркас | `mapper->UseLiquoriceStickSettings()` |

Есть смысл сверить свой `data/elements.json` с `vtkPeriodicTable`: цвета CPK,
ковалентные и ван-дер-ваальсовы радиусы. Совпадение — хороший абзац в записку,
расхождение — повод разобраться, чьи данные свежее.

## 7. Качество картинки

По умолчанию VTK выглядит как программа 2005 года: одна лампа, плоский свет,
лесенки на краях. Всё, ради чего затевалась третья версия, включается руками:

```cpp
renderer->SetUseSSAO(true);        // затенение в щелях между атомами —
renderer->SetSSAORadius(0.5);      // главный источник ощущения объёма
renderer->SetSSAOBias(0.01);
renderer->SetSSAOKernelSize(32);
renderer->SetSSAOBlur(true);

renderer->SetUseFXAA(true);        // сглаживание краёв
renderer->SetUseDepthPeeling(true);// честная прозрачность для орбиталей и НЭП
renderer->SetMaximumNumberOfPeels(8);

vtkNew<vtkLightKit> lights;        // трёхточечная студийная схема:
lights->AddLightsToRenderer(renderer);  // ключевой, заполняющий, контровой
```

Дальше по вкусу: `vtkShadowMapPass` в цепочке проходов рендера даёт тени;
`actor->GetProperty()->SetInterpolationToPBR()` вместе с металличностью и
шероховатостью — физически достоверные материалы.

Порядок работы над картинкой: сначала включить SSAO и свет и посмотреть, что
получилось. Скорее всего этого уже хватит, а тени и PBR окажутся украшением,
которое стоит своих хлопот только если останется время.

**Экспорт кадра.** `vtkWindowToImageFilter` с `SetScale(3)` и `vtkPNGWriter`
дают кадр 3000×2100 для пояснительной записки и презентации. Это то, чего во
второй версии нет вообще, и то, что сразу видно на защите.

## 8. Орбитали как изоповерхности — новая работа в ядре

Во второй версии лепестки гибридных орбиталей нарисованы кривыми Безье «на
глаз». Здесь они считаются.

В `chem/orbital.cpp` (Windows и VTK не знает, значит **проверяется тестами**):

Водородоподобные функции в атомных единицах, с точностью до нормировки:

* `2s`: ψ ∝ (2 − r) · e^(−r/2)
* `2p_z`: ψ ∝ z · e^(−r/2), и так же для `p_x`, `p_y`

Гибриды как их линейные комбинации:

* `sp³` вдоль направления **d**: ψ = ½·s + (√3/2)·p_**d**
* `sp²`: ψ = (1/√3)·s + (√2/√3)·p_**d**
* `sp`: ψ = (1/√2)·(s ± p_z)

где p_**d** = d_x·p_x + d_y·p_y + d_z·p_z — проекция набора p-орбиталей на
направление гибрида, а сами направления **уже посчитаны**: они лежат в
`AtomAnalysis::orbitalDirs` — единичные векторы всех гибридных орбиталей,
включая связывающие, которые ставит теория Гиллеспи. Придумывать их не надо,
надо только подставить.

Функция отдаёт значения на равномерной сетке в кубе вокруг центрального атома
(разумно 64³ точек на ±4 Å), а `scene/` кладёт их в `vtkImageData` и проводит
`vtkFlyingEdges3D` по двум уровням — `+iso` и `−iso`. Получаются две
поверхности, разного знака и разного цвета: ровно то, как орбитали рисуют
в учебниках, только посчитанное.

Что проверять в `tests/orbitaltest.cpp`:

1. нормировка: сумма ψ² по сетке, умноженная на объём ячейки, близка к единице;
2. узловая плоскость: у `p_z` значения при z = 0 равны нулю;
3. углы между гибридами: между четырьмя sp³ — 109,47°, между тремя sp² —
   120°, между двумя sp — 180°. Считается по положению максимума каждого
   гибрида;
4. ортонормированность: скалярное произведение разных гибридов по сетке — ноль,
   одинаковых — единица.

Пункт 3 стоит отдельного упоминания в записке: он показывает, что тетраэдрический
угол не постулируется, а получается из математики.

**Уточнено на этапе 5.** Три вещи в разделе выше при работе не подтвердились;
исправления вписаны сюда, а откуда они взялись — в разделе 11.

* **Направление гибрида ищется не по максимуму, а по первому моменту** ∫ψ·r dV.
  Максимума в смысле «положения лепестка» у этих функций нет: у водородоподобного
  гибрида наибольшее ψ приходится ровно на ядро (там 2s даёт 2a, а p — ноль),
  у слейтеровского в ядре ноль. Первый момент же лежит СТРОГО вдоль направления
  гибрида, и это доказывается в две строки: s-часть сферически симметрична и в
  момент не даёт ничего, а матрица ∫ρ·r_i·r_j dV у куба кратна единичной. Углы
  получаются с точностью до разрядности double, а не «примерно 109°».
* **Сетка 64³ на ±4 Å для нормировки мала.** Водородоподобные функции при Z = 1
  очень размазаны: внутри сферы радиусом 4 Å лежит лишь 77 % плотности 2s, и
  проверка нормировки дала бы 0,9. В проверках ящик ±8 Å с шагом 0,25 Å; сетке
  ПОКАЗА этого не требуется, там уровень берётся в долях от наибольшего |ψ|.
* **Рисуется не водородоподобная 2s, а слейтеровская.** Обе посчитаны и обе
  проверены, свойства у них одинаковы, а форма — нет; почему выбрана вторая,
  разобрано в разделе 11.

## 9. Наложения: что переехало в VTK, а что осталось

Дуги углов, облака неподелённых пар, стрелка диполя и подписи рисовались поверх
готового кадра VTK, а значит ложились поверх шаров даже тогда, когда должны были
за ними скрыться. Это и есть работа этапа 4. Но вещи в этом списке разной
природы, и мерить их одной меркой неправильно.

### 9.1. Протяжённые предметы — в VTK

**Дуги валентных углов.** Дуга обходит центральный атом: её ближняя половина
перед шаром, дальняя за ним. Точечной проверкой тут не обойтись — нужна
попиксельная, то есть VTK. Дуга строится как трубка (`vtkTubeFilter` по ломаной
из 36 точек), сектор между сторонами угла — веером треугольников. Толщина
трубки задаётся в ангстремах и растёт вместе с радиусом дуги: в пикселях это
даёт примерно ту же линию на любой молекуле и любом масштабе.

Свет дуге ни к чему, она светится сама: `SetAmbient(1)`, `SetDiffuse(0)`.

Геометрию считает `MoleculeRenderer::angleArcs()` — отбор по режиму показа и
текущему выбору, направления, радиус, цвет. Расчёт общий: сцена берёт из него
точки для трубки, а GDI+ — место для подписи. Иначе дуга и её подпись начали бы
жить каждая своей жизнью.

### 9.2. Текст — остаётся в GDI+, но получает проверку видимости

Переносить подписи в VTK было бы ошибкой. В `draw.h` объяснено, почему текст
рисуется обычным GDI **без сглаживания**: на тёмном фоне мелкий сглаженный
текст мылится, штрих размазывается по двум пикселям вполсилы, буквы слипаются
в пятно. Это выяснено пробой. VTK рисует текст через FreeType со своим
сглаживанием — тем самым, от которого уходили; вдобавок кириллица потребовала
бы `SetFontFile`, плашки подписей — отдельных актёров, а работающее разведение
подписей (`labelCollides`) пришлось бы выбросить.

Вместо этого — **аналитическая проверка видимости**, `render/occlusion.h`.
Сцена состоит из шаров, а пересечение луча с шаром — квадратное уравнение:
пускаем луч от глаза к точке и смотрим, не влезает ли по дороге чужой шар.
Видеокарту не спрашиваем вовсе, лишнего чтения кадра не появляется.

Для подписи проверяется не одна точка, а центр и четыре угла плашки —
прямоугольника в плоскости, перпендикулярной взгляду. Иначе подпись, закрытая
наполовину, продолжала бы читаться поверх чужого шара. Размер плашки известен
в пикселях, а перевод в ангстремы — это множитель `z / focal`.

Связи в проверку НЕ входят. Они тонкие и почти всегда закрыты самими шарами,
а ложные срабатывания дали бы охотно: связь выходит ровно из той точки, чью
видимость проверяют для подписи атома.

### 9.3. Облака неподелённых пар — остаются, но прячутся

Облако — мягкое пятно диаметром около трети ангстрема, то есть почти точка:
одной проверки видимости хватает. Закрытое наполовину исчезает целиком, а не
срезается по краю шара, но при таких размерах это заметно, только если
специально искать. Переносить их в `vtkPointGaussianMapper` можно, но это
означало бы заново подбирать вид свечения и включать прозрачность ради
результата, отличимого под лупой.

### 9.4. Стрелка диполя — намеренно поверх всего

Она не предмет сцены, а обозначение: заведомо длиннее молекулы и проходит
сквозь неё насквозь. Под ней специально нарисована тёмная подложка — чтобы
стрелка читалась и на светлых атомах. Отдать её на откуп глубине значило бы
спрятать половину. Проверки видимости у неё нет, и это не недоделка.

По той же причине поверх всего остаётся пунктирный отрезок, которым
обозначается линейный фрагмент (180°): пунктир — знак «дуги здесь нет», а не
предмет, и в VTK его пришлось бы изображать отдельными цилиндриками.

### 9.5. Лепестки орбиталей не трогаются

Они нарисованы кривыми Безье «на глаз», и раздел 8 их удаляет — вместо них
придут посчитанные изоповерхности. Переносить их в VTK значило бы делать
работу, которая через этап пойдёт в корзину.

### 9.6. Что стало с `renderer.cpp`

Раньше здесь было написано, что после этапа 4 он удаляется. **Это неверно.**
В нём остаются камера, проекция, проверка попадания мыши, фон со свечением и
сеткой, весь текст, облака пар, диполь и лепестки орбиталей. Файл перестал быть
рендером и стал видом; переименование разумно, но отдельным шагом и не сейчас.

## 10. Порядок работы

**Этап 1. Проба и переезд. СДЕЛАНО.** Раздел 3. Программа собирается через
CMake в MINGW64, работает как вторая версия, `ctest` проходит.

**Этап 2. Сцена вместо старого рендера. СДЕЛАНО.** `scene/frame.cpp` —
закадровый рендер и перенос кадра; `scene/scene.cpp` — `vtkMolecule` из
разбора, `vtkMoleculeMapper`, камера от собственного рендера. Шары и связи
рисует VTK, три стиля модели переключаются, дуги углов, НЭП, орбитали, диполь
и подписи пока рисуются по-старому поверх кадра.

Замеры на GT 1030, область сцены 662×721: **сцена 3,2 мс, перенос 0,5 мс**.
Перенос дешевле, чем в пробе, потому что `AlphaBlend` в память быстрее, чем
`StretchDIBits` в окно.

Что осталось за пределами этапа и ждёт следующих:

* НЭП и орбитали ложатся ПОВЕРХ шаров даже когда должны быть за ними —
  сортировки по глубине между GDI+ и VTK нет и быть не может (этап 4);
* подписи элементов и дуги углов тоже без проверки глубины (этап 4);
* анимации появления атомов больше нет — она жила в старом сборщике примитивов;
* затуманивание дальних атомов потеряно, вместо него на этапе 3 придут
  затенение и тени;
* цвета атомов — стандартная палитра CPK из VTK, а не своя, подогнанная под
  тёмный фон. Внутренняя таблица цветов `vtkMoleculeMapper` не подменяется,
  так что своя палитра потребует отказа от `DiscreteByAtom` (этап 3).

**Этап 3. Качество. СДЕЛАНО.** Раздел 7.

Включено: SSAO с радиусом выборки под размер атомов, FXAA, `vtkLightKit`
(он стоял с этапа 2), своя палитра вместо стандартной CPK, экспорт в PNG
кнопкой «Снимок».

Замеры там же, где и раньше (GT 1030, 662×721): **сцена 5,1 мс, перенос
0,5 мс**. Затенение и сглаживание обошлись в 1,9 мс, запас по кадру
по-прежнему втрое.

Что сделано НЕ было и почему:

* **Тени** (`vtkShadowMapPass`) не ставились. `SetUseSSAO` работает через
  собственную цепочку проходов рендерера, а тени требуют собрать цепочку
  вручную и подставить её через `SetPass`. Это ломает работающую настройку
  ради украшения, которое на молекуле из четырёх атомов почти не видно.
  Браться стоит, только если после этапа 5 останется время.
* **Прозрачность** (`SetUseDepthPeeling`) не включалась: в сцене VTK пока нет
  ни одного прозрачного предмета. Облака НЭП и лепестки орбиталей переедут
  туда на этапах 4 и 5 — тогда она и понадобится.
* **Затуманивание дальних атомов** не восстанавливалось. Его роль теперь
  играет затенение, и отдельная имитация тумана только спорила бы с ним.

**Этап 4. Наложения. СДЕЛАНО.** Раздел 9 — там разобрано, что переехало в VTK,
что осталось в GDI+ и почему. Коротко: дуги углов стали трубками в сцене,
подписи и облака пар получили аналитическую проверку видимости, стрелка диполя
намеренно оставлена поверх всего.

Замеры (GT 1030, 662×721, карбонат-ион в режиме «все углы»): **сцена 6,7 мс,
перенос 0,5 мс**. Полупрозрачные секторы стоят дороже дуг, но до бюджета кадра
в 16,7 мс всё равно вдвое.

**Этап 5. Орбитали. СДЕЛАНО.** Раздел 8.

Появился `chem/orbital.h/.cpp` — волновые функции 2s и 2p и гибриды sp, sp², sp³
на равномерной сетке, 173 строки, про Windows и про VTK не знает. Направления
гибридов, как и задумано, не выводятся заново: они берутся из
`AtomAnalysis::orbitalDirs`, куда их положила теория Гиллеспи.

`tests/orbitaltest.cpp` — 48 проверок, все зелёные:

| что | результат |
|---|---|
| нормировка 2s, 2p и каждого гибрида | 1 ± 0,0008 |
| узловая плоскость `p_z` при z = 0 | РОВНО ноль, не «почти» |
| ортогональность 2s ⊥ 2p, p_x ⊥ p_z | < 1e-9 |
| углы между осями sp³ / sp² / sp | 109,4712° / 120,0000° / 180,0000° |
| ортогональность разных гибридов | ≤ 0,0005 |
| то же на повёрнутом наборе и при Z = 3,2 | не меняется |

Углы сходятся до шестого знака, и это не совпадение: ось гибрида ищется через
первый момент, а он у куба точно кратен направлению (см. уточнение к разделу 8).
Ортогональность при этом — независимая проверка того же самого: гибриды с любым
другим углом между осями ортогональными не были бы.

В сцене: сетка кладётся в `vtkImageData`, `vtkFlyingEdges3D` проводит две
поверхности разного знака, полупрозрачные, разного цвета — фиолетовая ψ > 0,
оранжевая ψ < 0. Включено `SetUseDepthPeeling` с восемью слоями: до этого этапа
в сцене VTK не было ни одного прозрачного предмета, а теперь лепестки одного
атома пересекаются между собой.

`collectOrbitals` из `renderer.cpp` удалён — 78 строк кривых Безье. Вместо него
там остался отбор атомов (`MoleculeRenderer::orbitals`), 39 строк: какие атомы
показывать, каким зарядом ядра и в каком кубе. Расчёт — в ядре, показ — в сцене,
а выбор того и другого — в виде, ровно как с дугами углов.

Замеры там же, где и раньше (GT 1030, 662×721):

| случай | сцена | перенос |
|---|---|---|
| вода, орбитали одного атома | 10,4 мс | 0,5 мс |
| нитрат-ион, орбитали + все углы | 11,7 мс | 0,5 мс |
| пероксид водорода, восемь орбиталей (предел) | 14,9 мс | 0,5 мс |
| та же вода без орбиталей | 8,2 мс | 0,5 мс |

Бюджет кадра 16,7 мс выдержан, но запаса больше нет — весь он ушёл на
прозрачность. Дорог не расчёт (сетки пересчитываются только при смене молекулы
или выбранного атома), а послойная отрисовка: лепестки закрывают пол-экрана, и
каждый слой рисует их заново. Поэтому число орбиталей на экране ограничено
восемью, и поэтому же поверхности одного знака сшиваются в одного актёра —
на воде с орбиталями и всеми углами это сняло 3 мс из 15.

Что сделано НЕ было и почему:

* **Тени** (`vtkShadowMapPass`) так и не ставились. Причина прежняя (см. этап 3),
  и теперь к ней добавилась вторая: запаса по кадру не осталось.
* **Анимация появления орбиталей** не восстанавливалась. Лепестки Безье
  проявлялись плавно, потому что были дешёвыми; изоповерхность пересчитывать
  каждый кадр нельзя, а менять у неё прозрачность на лету — значит будить
  послойный разбор ещё чаще.

После этапа 4 `renderer.cpp` не удаляется — см. 9.6.

## 11. Грабли

Список составлен заранее, чтобы не терять на каждой по полдня.

* **Чёрный экран без единой ошибки** — забыт `vtk_module_autoinit` в
  `CMakeLists.txt`. Собирается, запускается, ничего не рисует. Это первое, что
  надо проверять при любой непонятной пустоте.
* **Не та оболочка.** Собирать только в `mingw64.exe`. В MSYS-оболочке другой
  компилятор, и VTK для него не собрана.
* **`find_package(VTK)` падает на «target not found».** Не хватает пакетов
  `nlohmann-json` и `fast_float`, которые VTK не объявляет зависимостями,
  см. раздел 3, шаг 5.
* **Зерно на шарах от SSAO.** Если радиус выборки взять «с запасом»
  (пробовал 1,6 радиуса самого крупного атома), выборка становится разреженной
  и по шарам идёт мелкая рябь, особенно на светлых. Рабочее значение — 0,8
  радиуса самого крупного атома при `SSAOKernelSize(64)` и `SSAOBias(0.02)`.
  Меньше нельзя: в объёмной модели перестанут темнеть щели между шарами,
  ради которых всё и делается.
* **Своя палитра вместо CPK.** Таблицу цветов у `vtkMoleculeMapper`
  подменить нельзя, она внутренняя. Но `GetPeriodicTable()` отдаёт наружу
  `vtkBlueObeliskData`, а у него `GetDefaultColors()` — изменяемый массив
  RGB по номеру элемента. Записать туда свои цвета надо ДО первого рендера,
  иначе маппер успеет построить таблицу по старым.
* **`CustomArrayRadius` молча не работает.** Массив `radii` добавлен в
  `molecule->GetAtomData()`, имя правильное, тип `float` — а маппер рисует
  ПУСТОТУ. Причина: конвейер VTK смотрит на время изменения ВХОДА, и
  `AddArray` его не поднимает. Лечится `molecule->Modified()` сразу после
  `AddArray`. Ошибки нет ни при сборке, ни при запуске.
* **Кадр переносится, а на экране ничего.** Прежде чем искать причину в VTK,
  стоит проверить сам цикл переноса: на этапе 2 указатель приёмника не
  двигался по строке, писался только первый пиксель каждой строки. Со стороны
  выглядело в точности как неработающая прозрачность. Полезный приём для
  разбора: выгрузить кадр в `.bmp` прямо из программы и посмотреть на него —
  это сразу отделяет «VTK не нарисовала» от «перенос сломан».
* **Молекула вышла крошечной посреди пустого кадра.** `ResetCamera()` позвана
  до первого `Render()`: маппер геометрию ещё не построил, границы сцены пусты,
  и камера наводится в никуда. Наводить камеру надо после первого кадра.
  На этом споткнулась проба при первом запуске.
* **Смешивание с w64devkit.** Если в `PATH` окажется его g++, сборка пройдёт,
  а программа упадёт при запуске: у сборок libstdc++ разный ABI.
* **Кириллица в подписях VTK.** Встроенный шрифт её не знает, вместо букв будут
  прямоугольники. Лечение:
  `property->SetFontFamily(VTK_FONT_FILE)` и
  `property->SetFontFile("C:/Windows/Fonts/segoeui.ttf")`.
* **DLL рядом с программой.** Список зависимостей снимается через
  `ldd build/molview.exe`, всё из `mingw64/bin` копируется рядом с `.exe`.
  Готового инструмента для этого у VTK нет; скрипт написан — `tools/distr.sh`,
  см. 13.1.
* **`ldd` не в той оболочке молча врёт.** Он есть не только в MSYS2: Git Bash
  приносит свой. Тот же `ldd build/molview.exe` в нём отработает без единой
  ошибки и покажет ТРИ библиотеки вместо шестидесяти семи — просто потому,
  что VTK нет в его `PATH`, и до неразрешённых зависимостей дело не доходит.
  Дистрибутив из такого списка собирается, весит 3 МБ и не запускается нигде,
  кроме машины сборки. Поэтому `distr.sh` первым делом проверяет
  `MSYSTEM = MINGW64` и отказывается работать, если ldd не нашёл ничего
  в `/mingw64`.
* **Статическая компоновка.** Флаги `-static-libstdc++` и прочие надо убрать
  из `CMakeLists.txt`, когда появится VTK, иначе компоновка не сойдётся.
* **`CMAKE_BUILD_TYPE`.** Если не задать, CMake собирает без оптимизации.
  В `CMakeLists.txt` это уже предусмотрено, но при ручной настройке легко
  потерять и потом удивляться, почему всё медленно.
* **Направления у гибрида нет в его максимуме.** Проверка «углы считаются по
  положению максимума каждого гибрида» не работает ни на одной из двух форм
  2s. У водородоподобной наибольшее ψ приходится РОВНО НА ЯДРО: там 2s даёт
  2a, p-часть ноль, и дальше функция только убывает во все стороны. У
  слейтеровской в ядре ноль. На сетке «максимум» окажется в случайном узле
  рядом с центром, и угол между такими «направлениями» — шум. Работает первый
  момент ∫ψ·r dV: он лежит строго вдоль d, потому что s-часть в момент не даёт
  ничего, а матрица ∫ρ·r_i·r_j dV у куба кратна единичной (внедиагональные
  члены нечётны, диагональные равны по симметрии куба). Точность — шестой знак
  после запятой, и от поворота сетки она не зависит.
* **Водородоподобный гибрид посчитан верно, а смотреть на него нельзя.**
  Это главная неожиданность этапа, и на неё ушло два захода с картинкой.
  У водородоподобной 2s есть радиальный узел при r = 2: дальше него она
  отрицательна. В гибриде отрицательная часть выходит не маленьким лепестком
  назад, а ШИРОКИМ КОНУСОМ — при большом r знак ψ определяется условием
  cos θ < (r − 2)/(√3·r), а это θ > 54,7° независимо от уровня. Четыре
  sp³-орбитали кислорода такими конусами закрывают всю сферу, и вместо
  тетраэдра на экране оранжевый шар. Отношение объёмов ψ < 0 и ψ > 0 на сетке
  выходит 5,6 — это и проверяется в `orbitaltest`, чтобы наблюдение не
  потерялось.
  Лечение — приближение Слейтера: ψ₂s ∝ r·e^(−r/2), узла нет. Тогда
  sp³ ∝ r·e^(−r/2)·(1 + 3cos θ), обратный лепесток ровно вдвое слабее
  переднего, а узловая поверхность оказывается конусом под 109,47° — тем самым
  тетраэдрическим углом. То же отношение объёмов становится 0,14. Считаются и
  проверяются ОБЕ формы (свойства у них одинаковы), а рисуется слейтеровская.
* **Орбитали атома водорода крупнее самой молекулы.** Формулы задания записаны
  при Z = 1, то есть это возбуждённый АТОМ ВОДОРОДА: его 2p тянется на 2 Å при
  длине связи O–H 0,96 Å. Лечение — эффективный заряд ядра, r → Z·r с
  нормировкой ×Z^(3/2). Берётся он из условия «радиус наибольшей плотности
  p-части (4/Z боровских радиусов) равен ковалентному радиусу элемента»: тогда
  лепесток дотягивается примерно до соседнего атома, а разные элементы
  отличаются размером орбитали так же, как отличаются размером сами. На
  проверяемых свойствах заряд не сказывается никак — он меняет только масштаб
  длины, и в `orbitaltest` это отдельная проверка.
* **Один уровень изоповерхности на оба знака не годится.** Обратный лепесток
  слабее переднего вдвое у sp³ и вчетверо у sp. Поставишь уровень так, чтобы
  он был виден, — передние лепестки четырёх sp³ раздуются и сольются в шар;
  поставишь так, чтобы они разделялись, — обратного не будет вовсе ни у sp, ни
  у sp². Поэтому уровни берутся порознь: положительный — доля от наибольшего ψ
  на сетке, отрицательный — доля от наименьшего.
* **Первые уровни (0,45 и 0,55) дали кляксу, а не тетраэдр.** Цифры
  подбирались так, чтобы обратный лепесток был виден, — и он вышел почти с
  передний (1,26 ковалентного радиуса против 1,42), а передний при 0,45 —
  яйцо шире собственной длины (полуширина 0,9 радиуса). Четыре таких sp³
  вокруг кислорода сливались в сплошной шар. Взяты 0,7 и 0,8: передний
  лепесток — капля длиной 1,05 радиуса и полушириной 0,55, кончик касается
  шара соседа; обратный — хвостик длиной 1,0, из шара атома (0,5 радиуса)
  выглядывает наполовину. Правило здесь одно: программа учебная, и
  **понятность картинки важнее её точности** — уровень изоповерхности всё
  равно выбор показа, а не физики.
* **Цвет лепестка — по назначению, а не по знаку ψ.** Во второй версии
  орбитали неподелённых пар красились иначе, чем связывающие, и в переезде
  на изоповерхности это потерялось: два цвета ушли на два знака. Для
  школьника же главное в картинке воды — «эти две смотрят на водороды, а эти
  две заняты парами, потому угол 104,5°, а не 109,5°». Поэтому передние
  лепестки связей и пар — двух цветов (пары — цветом облака НЭП), обратные
  лепестки всех орбиталей — третьим. Знак не теряется: обратный лепесток
  всегда отдельного цвета.
* **Водородоподобная 2s не выброшена, а стала режимом «Как считается».**
  Кнопка рядом с «Орбитали» переключает радиальную часть на ту, что записана
  в задании, — с узлом. На экране положительная часть прячется в ядре, а
  отрицательная торчит четырьмя конусами наружу. Это не рабочий вид, а
  демонстрация для защиты: живьём показать, ПОЧЕМУ в учебниках рисуют
  слейтеровскую форму, и что «посчитано верно» и «понятно» — не одно и то же.
* **Прозрачность стоит не расчёта, а отрисовки.** Пересчёт сеток идёт только
  при смене молекулы или выбранного атома, и на кадр не влияет вовсе. А вот
  `SetUseDepthPeeling` рисует сцену заново на каждый слой, и лепестки, которые
  закрывают пол-экрана, платят за это полную цену. Четыре орбитали одного
  атома — это восемь актёров против двух, если поверхности одного знака сшить
  `vtkAppendPolyData`; сшивание сняло 3 мс из 15. Число орбиталей на экране
  пришлось ограничить восемью — заодно и к лучшему: полупрозрачные лепестки
  соседних атомов всё равно превращаются в муть.
* **Само включение `SetUseDepthPeeling` стоит около полутора миллисекунд**
  даже когда прозрачных предметов в кадре нет: вода без орбиталей была 6,7 мс,
  стала 8,2 мс. Плата за то, что заливки секторов валентных углов перестали
  зависеть от порядка отрисовки.
* **Если закадровый рендер не заработает** (проба показывает чёрный кадр,
  хотя `autoinit` на месте) — отступаем к дочернему окну: убрать
  `SetShowWindow(false)` и `SetUseOffScreenBuffers(true)`, позвать
  `SetParentId(hwnd)`. Тогда раздел 5 отменяется, панель инструментов и
  заголовок выносятся полосами над и под областью сцены, а `panel.cpp`
  правится в части раскладки.

## 12. Соглашения

Те же, что во второй версии:

* C++17, `-Wall -Wextra`, без предупреждений;
* исходники в UTF-8, сборка с `-finput-charset=UTF-8 -fexec-charset=UTF-8`,
  Windows API — широкими строками;
* комментарии и строки интерфейса по-русски, комментарии объясняют **почему**;
* именование: типы `PascalCase`, функции и переменные `camelCase`;
* заголовки самодостаточны, `#pragma once`;
* **никаких «улучшений» алгоритмов ядра по ходу дела.** Калибровочные
  константы, веса групп, коэффициенты релаксации, масштаб диполя — не трогать:
  эталон снят именно с ними.

## 13. Критерии готовности

1. `grep -rE "windows.h|vtk" src/chem/` пусто.
2. `ctest --test-dir build` — все 89 молекул сходятся с эталоном, средняя
   ошибка валентного угла 1,68°.
3. Программа открывается, молекула вращается мышью, колесо меняет масштаб,
   щелчок по атому открывает разбор.
4. Работают все три стиля модели, НЭП, орбитали, диполь, режимы показа углов.
5. Видно затенение в углублениях между атомами — то, чего нет во второй версии.
6. Орбитали — посчитанные изоповерхности, и `orbitaltest.exe` подтверждает
   углы 109,47° / 120° / 180°.
7. Кнопка сохранения даёт PNG размером не меньше 3000 пикселей по ширине.
8. Программа запускается на другой машине: папка с `.exe` и DLL скопирована
   целиком, MSYS2 там не установлен.

### 13.1. Дистрибутив

Собирается `tools/distr.sh` из оболочки MINGW64 — из PowerShell так:

```
$env:MSYSTEM='MINGW64'
& C:\msys64\usr\bin\bash.exe -lc "/c/git/fun/molviewvtk/tools/distr.sh"
```

Скрипт пересобирает программу, складывает в `distr/` её саму, каталог `data/`
и все библиотеки, которые перечислил `ldd`, а в конце проверяет сам себя:
запускает `ldd` уже НА КОПИИ и убеждается, что ни одна ссылка не уходит
в `/mingw64`. Windows ищет DLL сначала рядом с программой, поэтому такой
прогон показывает ровно то, чем папка будет пользоваться на чужой машине.

Выходит 72 файла и около 137 МБ: 67 библиотек VTK и её зависимостей, из них
одна `libvtkCommonCore.dll` — 58 МБ. Они уже без отладочной информации,
`strip` не убирает ни байта; это та самая «осознанная плата за библиотеку»
из раздела 2. Единого `.exe`, как во второй версии, здесь не будет.

Ключ `--with-tests` кладёт рядом и консольные проверки. Они собраны
статически, своих библиотек не тянут, а `data/` находят рядом с собой —
то есть сверку с эталоном можно прогнать прямо из скопированной папки,
не имея ни исходников, ни компилятора.

В `distr/` кладётся и `ЧИТАЙ.txt` — для того, кто получит папку: что
запускать, что ставить ничего не нужно и что копировать её надо целиком.

## 14. Чего делать не надо

* **Не переходить на Qt.** Интерфейс уже написан и работает; переписывать его
  на виджеты — потерянная неделя без единого нового результата на экране.
* **Не звать `interactor->Start()`.** Цикл сообщений свой.
* **Не подключать OSPRay и трассировку лучей.** Это отдельная зависимость,
  и SSAO с тенями даёт девять десятых эффекта за одну сотую хлопот.
* **Не добавлять молекул в базу** — она общая с первой версией, любое
  расхождение ломает сверку с эталоном.
* **Не переносить `chem/` на структуры данных VTK.** Соблазн есть:
  у `vtkMolecule` тоже есть атомы и связи. Но тогда ядро перестанет быть
  проверяемым отдельно, а вместе с ним исчезнет и ответ на вопрос, что в
  проекте сделано своими руками.
